# Account, usage, billing and pricing routes

Read and update your account, read usage, billing and prices, manage notifications, and sign in.

Every route is on `https://sandbox.tangle.tools` and takes your account API key as `Authorization: Bearer <key>` unless it says otherwise. Errors use the shape in [Error codes](/sandbox/errors).
This page is generated from the [OpenAPI document](/sandbox-openapi.json), which also has every response schema.

### Resolve a model credential for an agent profile

`POST /v1/model-credentials/resolve`

Selects a model-credential seat for the profile and returns how to reach it: a CLI auth reference or an API key environment variable with its base URL. The response never holds a raw key and is never cached. Only the principal enrolled for the deployment's account-owner grant can call it; other callers, keys scoped to one sandbox and member-paid line keys get 403. A retained sandbox must be one the caller owns personally.

Request body (`application/json`):

| Field | Type | Required | Description |

### Get egress pricing

`GET /v1/pricing/egress`

Each plan's monthly egress allowance and the price beyond it. Public: no credential is required. Outbound bytes from each sandbox are counted per UTC calendar month; inbound traffic is free. Every plan's allowance is per account (`scope: account`), shared by its sandboxes: `overage: billed` plans pay `usdPerGb` per decimal GB (10^9 bytes) beyond `includedBytes`; `overage: refused` plans are refused new sandboxes and prompts at it and never charged. Computed from the allowances quota admission enforces and the rates this deployment bills.

| Status | Meaning |
|---|---|
| 200 | Egress terms retrieved |

### Get the sandbox rate card

`GET /v1/pricing/sandboxes`

USD per vCPU-hour, per GB-hour of memory, per GB-hour of disk, and the hourly minimum, for the pool this deployment bills sandboxes in. A sandbox is billed vcpu*cpuCoreHourUsd + memoryGB*memoryGBHourUsd + diskGB*diskGBHourUsd per hour, floored at minChargeHourUsd. `source` is `pool-derived` when the numbers come from the configured pool's own host cost and sellable capacity, and `reference-constants` when no pool cost is configured and the deployment prices on the pricing engine's reference server instead. Public: no credential is required.

| Status | Meaning |
|---|---|
| 200 | Rate card retrieved |

### Delete the account

`DELETE /auth/account`

Takes the `session` cookie, or its token as a Bearer token, from a browser sign-in; an API key, CLI token or runtime token gets 403 `SESSION_AUTH_REQUIRED`. It also needs the `recent_auth` cookie that sign-in sets, which expires soon after. Marks the account deleted, revokes the API keys Sandbox created for it, except a team's keys, and clears the `session` cookie.

Authentication: a browser session cookie.

| Status | Meaning |
|---|---|
| 200 | Account deleted |
| 401 | No valid credential, or no `recent_auth` cookie from a recent sign-in |
| 403 | Key verification refused the credential, or an API key, CLI token or runtime token called a route that needs a browser sign-in (`SESSION_AUTH_REQUIRED`) |
| 500 | The account could not be deleted |
| 502 | Key verification returned an incomplete identity |
| 503 | Key verification is unavailable; retry after the `Retry-After` seconds |

### Finish browser sign-in

`GET /auth/callback`

Takes the one-time `code` from Tangle sign-in and the `oauth_state` cookie set when sign-in started. Always answers with a redirect. On success it sets the `session` and `recent_auth` cookies and redirects to the `redirect_to` target from sign-in, by default `/dashboard`. When the account has two-factor sign-in on, it sets the `mfa_challenge` cookie and redirects to the dashboard `/mfa` page instead. A CLI sign-in redirects to its loopback `callback_url` with `grant_token`, `expires_at` and `session_expires_at`; exchange the `grant_token` at `POST /auth/cli/exchange`. On failure it redirects to `/login?error=<reason>` on the dashboard, or to the loopback `callback_url` with `error=<reason>`. Reasons include `missing_code`, `csrf_mismatch`, `auth_failed`, `email_verification_required` and `paid_access_required`.

Authentication: none.

| Parameter | In | Required | Type | Description |
|---|---|---|---|---|
| `code` | query | No | string | One-time code that Tangle sign-in returns. |
| `state` | query | No | string | State value from the sign-in redirect, returned unchanged. |
| `error` | query | No | string | Error code from Tangle sign-in, when sign-in failed there. |
| `error_description` | query | No | string | Readable reason for `error`; the redirect uses it when present. |

| Status | Meaning |
|---|---|
| 302 | Redirect to the dashboard, the two-factor page, the CLI loopback URL, or the login page with an error |
| 429 | Too many requests from this address; wait `Retry-After` seconds |
| 503 | The rate limiter is unavailable; retry shortly |

### Replace backup codes

`POST /auth/mfa/backup-codes`

Takes the `session` cookie, or its token as a Bearer token, from a browser sign-in; an API key, CLI token or runtime token gets 403 `SESSION_AUTH_REQUIRED`. It also needs the `recent_auth` cookie that sign-in sets, which expires soon after. Needs a current code. The old backup codes stop working.

Authentication: a browser session cookie.

Request body (`application/json`):

| Field | Type | Required | Description |
|---|---|---|---|
| `code` | string | Yes | Current code from the authenticator app, or an unused backup code. |

| Status | Meaning |
|---|---|
| 200 | New backup codes |
| 400 | `code` is wrong |
| 401 | No valid credential, or no `recent_auth` cookie from a recent sign-in |
| 403 | Key verification refused the credential, or an API key, CLI token or runtime token called a route that needs a browser sign-in (`SESSION_AUTH_REQUIRED`) |
| 404 | Two-factor sign-in is not on |
| 500 | The two-factor change failed |
| 502 | Key verification returned an incomplete identity |
| 503 | Key verification is unavailable; retry after the `Retry-After` seconds |

### Complete a two-factor sign-in

`POST /auth/mfa/challenge`

Takes the `mfa_challenge` cookie that sign-in sets when the account has two-factor sign-in on, and a current code or an unused backup code. On success it sets the `session` and `recent_auth` cookies and clears `mfa_challenge`. Each correct submission uses up the cookie. A wrong code sets a fresh `mfa_challenge` cookie with the same expiry; use it for the retry. For a CLI sign-in, `redirect_to` is the loopback `callback_url` carrying the `grant_token` for `POST /auth/cli/exchange`.

Authentication: the two-factor challenge cookie from sign-in.

Request body (`application/json`):

| Field | Type | Required | Description |
|---|---|---|---|
| `code` | string | Yes | Current code from the authenticator app, or an unused backup code. |

| Status | Meaning |
|---|---|
| 200 | Signed in |
| 400 | `code` is wrong |
| 401 | No challenge cookie, an expired one, or the sign-in no longer passes key verification |
| 403 | The sign-in has no key binding, or key verification refused it |
| 409 | Another challenge is in progress for this account, or this cookie was already used |
| 429 | Too many requests from this address; wait `Retry-After` seconds |
| 502 | Key verification returned an incomplete identity |
| 503 | Key verification or the rate limiter is unavailable; retry shortly |

### Start two-factor enrollment

`POST /auth/mfa/enroll`

Takes the `session` cookie, or its token as a Bearer token, from a browser sign-in; an API key, CLI token or runtime token gets 403 `SESSION_AUTH_REQUIRED`. It also needs the `recent_auth` cookie that sign-in sets, which expires soon after. Returns a new secret and backup codes. Two-factor sign-in stays off until `POST /auth/mfa/verify` accepts a code from the secret.

Authentication: a browser session cookie.

| Status | Meaning |

| 502 | Key verification returned an incomplete identity |
| 503 | Key verification is unavailable; retry after the `Retry-After` seconds |

### Finish two-factor enrollment

`POST /auth/mfa/verify`

Takes the `session` cookie, or its token as a Bearer token, from a browser sign-in; an API key, CLI token or runtime token gets 403 `SESSION_AUTH_REQUIRED`. It also needs the `recent_auth` cookie that sign-in sets, which expires soon after. Turns on two-factor sign-in when `code` matches the secret from `POST /auth/mfa/enroll`.

Authentication: a browser session cookie.

Request body (`application/json`):

| Field | Type | Required | Description |
|---|---|---|---|
| `code` | string | Yes | Current code from the authenticator app. |
| `backup_codes` | array of string | Yes | The `backup_codes` that `/enroll` returned, unchanged. |

| Status | Meaning |
|---|---|
| 200 | Two-factor sign-in is on |
| 400 | `code` is wrong, or `backup_codes` is not the list `/enroll` returned |
| 401 | No valid credential, or no `recent_auth` cookie from a recent sign-in |
| 403 | Key verification refused the credential, or an API key, CLI token or runtime token called a route that needs a browser sign-in (`SESSION_AUTH_REQUIRED`) |
| 404 | No enrollment is pending, or it expired; start again with `/enroll` |
| 500 | The two-factor change failed |
| 502 | Key verification returned an incomplete identity |
| 503 | Key verification is unavailable; retry after the `Retry-After` seconds |
